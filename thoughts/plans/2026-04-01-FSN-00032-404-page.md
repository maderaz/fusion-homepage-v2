# 404 Page Implementation Plan

## Overview

Create a simple, centered 404 page for both sites (fusion.ipor.io and ipor.io). When a user navigates to a non-existent path, they see a clean "Page Not Found" screen with a link back to home. A shared content component keeps both sites consistent. Visual (Playwright) tests verify rendering.

## Current State Analysis

- No 404 page exists in either site
- Astro convention: `pages/404.astro` generates `404.html` at build time
- AWS Amplify natively serves `404.html` for missing routes
- Both sites share `BaseLayout`, `Footer`, and `CookieBanner`
- Each site has its own `Nav` component

### Key Discoveries:

- Page pattern: `BaseLayout` → `Nav` → content → `Footer` → `CookieBanner` (e.g., `src/sites/fusion/pages/privacy-policy.astro:9-17`)
- Section container: `mx-auto max-w-[1200px] px-6` used everywhere
- Primary CTA button: `brand-gradient inline-flex items-center justify-center rounded-full border border-primary px-7 py-3 text-sm font-semibold text-white transition-opacity hover:opacity-70`
- Playwright uses `npx serve dist -l 4567 -s` — the `-s` (SPA) flag rewrites missing paths to `index.html`, so tests must navigate to `/404.html` directly
- Console-errors tests iterate over a `pages` array (`tests/visual/fusion/console-errors.spec.ts:3`) — we add `/404.html` there
- Visual tests follow pattern: light mode + dark mode screenshots with `maxDiffPixelRatio: 0.01`

## Desired End State

- Visiting any non-existent path on either site shows a styled 404 page
- The page includes the site's nav, a centered "Page Not Found" message, a "Back to Home" button, and the shared footer
- Visual tests confirm the page renders correctly in both themes on both sites
- No console errors on the 404 page

### How to Verify:

1. `npm run build:fusion && npx serve dist -s` → visit `http://localhost:3000/nonexistent` or `/404.html`
2. `npm run build:ipor && npx serve dist -s` → same check
3. `npm run test:visual:fusion` and `npm run test:visual:ipor` pass (after updating snapshots)

## What We're NOT Doing

- No animated illustrations or complex visuals — simple centered text
- No React islands — pure Astro component, no client-side interactivity
- No unit tests — there's no testable logic; visual tests are the right tool here
- No changes to the `serve` command or Playwright config beyond adding test files
- No custom error pages for other HTTP status codes (500, etc.)

## Implementation Approach

1. Create a shared `not-found-content.astro` component with the centered layout
2. Create `404.astro` in each site's `pages/` directory, wiring up the site-specific nav
3. Add Playwright visual tests (screenshot + console-error coverage)

## Phase 3: Configure AWS Amplify 404 Rewrite

### Overview

Amplify does **not** automatically serve `404.html` for missing routes. A rewrite rule must be added in the Amplify Console for each app (fusion and ipor).

### Changes Required:

This is a **manual step** in the AWS Amplify Console (redirects cannot be configured via `customHttp.yml` or any committed file — only via the Console UI or CloudFormation/Terraform).

For **both** the Fusion and IPOR Amplify apps:

1. Go to **Amplify Console → Hosting → Rewrites and redirects**
2. Add the following rule as the **last entry** (it must not precede other more-specific rules):

| Source | Target      | Status | Type    |
| ------ | ----------- | ------ | ------- |
| `/<*>` | `/404.html` | `404`  | Rewrite |

JSON form:

```json
[
  {
    "source": "/<*>",
    "target": "/404.html",
    "status": "404",
    "condition": null
  }
]
```

**Important**: Use status `404`, not `404-200`. The `404-200` variant returns HTTP 200, which is bad for SEO and misleads crawlers.

## Phase 4: Add Playwright Visual Tests

### Overview

Add visual screenshot tests and console-error coverage for the 404 pages on both sites.

### Changes Required:

#### 1. Fusion 404 Visual Test

**File**: `tests/visual/fusion/404.spec.ts` (new)

Following the pattern from `tests/visual/fusion/nav.spec.ts`:

```typescript
import { test, expect } from "@playwright/test";

test.setTimeout(60_000);

test.beforeEach(async ({ page }) => {
  await page.addInitScript(() => {
    localStorage.setItem("cookie_consent", "declined");
  });
});

test("404 page - light mode", async ({ page }) => {
  await page.goto("/404.html", { waitUntil: "networkidle" });
  await page.evaluate(() => document.documentElement.classList.remove("dark"));
  await page.waitForTimeout(500);
  await expect(page).toHaveScreenshot("404-light.png", {
    maxDiffPixelRatio: 0.01,
  });
});

test("404 page - dark mode", async ({ page }) => {
  await page.goto("/404.html", { waitUntil: "networkidle" });
  await page.evaluate(() => document.documentElement.classList.add("dark"));
  await page.waitForTimeout(500);
  await expect(page).toHaveScreenshot("404-dark.png", {
    maxDiffPixelRatio: 0.01,
  });
});
```

Notes:

- Navigate to `/404.html` directly (not a random path) because `serve -s` rewrites unknown paths to `index.html`
- Full page screenshot (not a specific locator) since the page is simple and self-contained

## Testing Strategy

### Visual Tests (Playwright):

- Full-page screenshots of 404 page in light and dark mode (both sites)
- Console error/warning checks on 404 page in both themes (both sites)

### No Unit Tests:

The 404 page is a static Astro component with zero logic — no state, no props, no conditionals. Visual tests are the appropriate testing strategy.

## Performance Considerations

None — this is a simple static HTML page with no client-side JavaScript, no API calls, and no images to optimize.
